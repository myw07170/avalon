# 架构边界

本文档记录**为什么这样分层**，以及各层之间不能越过的界限。

三份核心文档的分工：[rules.md](./rules.md) 是规则依据，[state-machine.md](./state-machine.md) 是引擎设计，本文档记录分层边界。边界决策不属于规则或状态机细节，所以单独立此文件。

新增一层、引入一个外部服务、或者想让某层直接读另一层的数据之前，先看这里。

## 1. 分层与依赖方向

```
运营层    账号 / 额度 / 计费             可选公开部署能力，唯一需要数据库的一层
   |
   |  只在 /api/* 的入口处做鉴权与扣费，不向下传递任何信息
   v
UI 层     React 组件 + Jotai            只读 viewAtom
   |
   v
AI 层     prompt 构建 / provider 调用    唯一允许发网络请求的地方
   |
   |  输入只有 PlayerView
   v
引擎      纯函数 reducer                禁止 fetch / Date.now / Math.random
```

依赖方向**单向向下**。核心约束：**引擎不知道上面三层的存在**。

引擎里没有 `userId`，没有 `sessionToken`，没有"这局是不是付费用户开的"。`GameState` 和 `PlayerView` 里永远不会出现账号字段。即使公开部署启用了账号体系，这条依然成立——运营层挂在 `/api/*` 的入口上，和游戏逻辑之间只隔着一次鉴权，不共享任何数据结构。

## 2. 引擎不依赖数据库，恢复存档由驱动层负责

三条理由，每条都独立成立：

**引擎是纯函数 reducer。** 见 [state-machine.md §3](./state-machine.md)：不发网络请求，不调 LLM，不读时间戳，随机源作为参数注入。它没有任何需要外部存储的状态——`reduce(state, action, rng)` 的输出完全由输入决定。

**游戏循环仍在浏览器执行。** `/api/ai` 转发模型请求；账号部署额外通过存档 Route Handlers 保存和恢复检查点。人设来自随仓库发布的静态目录，游戏开局不经过服务端生成人设。

**引擎状态仍可序列化。** 进行中存档还需包含随机数状态和并发批次中已收到、尚未提交的操作，才能从等待中的回合继续。账号部署保存到云端，本地部署保存到浏览器；两种存储共用检查点结构。

## 3. 数据库职责

**服务于账号、额度、复盘历史和跨设备恢复。**

`active_games` 保存账号唯一的进行中检查点，`game_sessions` 保存计费会话和终局复盘。完整检查点只在驱动层和存档服务之间传递，组件仍只读批准过的视图。

引擎、AI prompt 和 `GameState` 仍然不知道 `userId`、数据库表或计费信息。写入代次、租约与会话 ID 都保存在引擎状态之外，详见[进行中对局恢复](game-recovery.md)。

账号余额、复盘和恢复检查点需要跨设备共享；未提交的输入草稿、动画状态和模型 API Key 不进入存档。

## 4. 与 wolfcha 的对比

参考项目 [oil-oil/wolfcha](https://github.com/oil-oil/wolfcha) 的 `.env.example` 里有 Supabase 配置，容易让人以为做这类游戏就得配数据库。把那个文件整体拆开看就清楚了：

| 配置 | 用途 | 属于哪一层 |
| --- | --- | --- |
| `STRIPE_SECRET_KEY` / `STRIPE_PRICE_ID` | 支付订阅 | 运营 |
| `WATCHA_CLIENT_ID` / `SECRET` | 第三方 OAuth 登录 | 运营 |
| `SUPABASE_URL` / `SERVICE_ROLE_KEY` | 数据库 + 认证 | 运营 |
| `MINIMAX_TTS_MODEL` | 语音合成 | 表现层 |
| `ZENMUX` / `DASHSCOPE` / `NEWAPI` 等 | LLM provider | AI 层 |

Supabase 在那里是和 Stripe、OAuth 并列的——它服务的是**公开运营的商业产品**（wolf-cha.com 是线上服务）所需的账号与订阅配额。狼人杀的规则本身一行都不需要它。

所以核心游戏没有数据库，不是漏了，是范围不同。只有在公开 remote 部署需要账号、额度和预算防线时，才会因为**同样的运营原因**引入它。

## 5. 什么情况下需要重新审视本文档

以下任何一条成真，本文件的结论就要重新评估：

- 要做**线上多人对局**（真人对真人）——需要实时同步与权威服务端，引擎的运行位置会变
- 要做**排行榜或跨设备战绩**——对局数据就有了跨会话查询的需求
- 要做**对局数据分析**（比如统计各模型胜率并长期留存）

目前这三条都不在核心范围内。多模型对战胜率统计这类实验可以单机跑完即看，不需要默认落库。
