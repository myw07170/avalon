# 架构边界

本文档记录**为什么这样分层**，以及各层之间不能越过的界限。

三份文档的分工：[rules.md](./rules.md) 是规则依据，[state-machine.md](./state-machine.md) 是引擎设计，[todos.md](./todos.md) 是路线图。边界决策不属于其中任何一份，所以单独立此文件。

新增一层、引入一个外部服务、或者想让某层直接读另一层的数据之前，先看这里。

## 1. 分层与依赖方向

```
运营层    账号 / 额度 / 计费             阶段 7，唯一需要数据库的一层
   |
   |  只在 /api/* 的入口处做鉴权与扣费，不向下传递任何信息
   v
UI 层     React 组件 + Jotai            只读 myViewAtom
   |
   v
AI 层     prompt 构建 / provider 调用    唯一允许发网络请求的地方
   |
   |  输入只有 PlayerView
   v
引擎      纯函数 reducer                禁止 fetch / Date.now / Math.random
```

依赖方向**单向向下**。核心约束：**引擎不知道上面三层的存在**。

引擎里没有 `userId`，没有 `sessionToken`，没有"这局是不是付费用户开的"。`GameState` 和 `PlayerView` 里永远不会出现账号字段。加了账号体系之后这条依然成立——运营层挂在 `/api/ai` 的入口上，和游戏逻辑之间只隔着一次鉴权，不共享任何数据结构。

## 2. 为什么引擎和对局数据不需要数据库

三条理由，每条都独立成立：

**引擎是纯函数 reducer。** 见 [state-machine.md §3](./state-machine.md)：不发网络请求，不调 LLM，不读时间戳，随机源作为参数注入。它没有任何需要外部存储的状态——`reduce(state, action, rng)` 的输出完全由输入决定。

**服务端代码全都是无状态的。** 一共两个 Route Handler——`/api/ai`（对局中的每次决策）与 `/api/personas`（开局生成一桌人设），存在的理由完全相同：别让 LLM 的 API key 进浏览器。两个都只转发一次请求、返回一次结果，不记录任何东西。

**一整局 = `seed + action[]`，几百字节。** 因为引擎确定性，同一个种子加同一串动作必然重放出同一局。存档不需要数据库，一个 JSON 文件就够。这正是 [todos.md](./todos.md) 阶段 6「对局导出，导入可完整重放」那条的底气——它是文件级的，本来就与数据库无关。

## 3. 数据库的唯一职责

**只服务于账号、额度、计费这条运营线**（阶段 7）。

**不存对局数据。** 对局数据没有跨设备、跨用户查询的需求，存进去只是增加隐私面和运维成本。玩家想留存一局，导出 JSON 即可。

判断某样东西该不该进数据库，问一句：**它需要在不同设备、不同会话之间共享吗？** 账号余额需要，对局记录不需要。

## 4. 与 wolfcha 的对比

参考项目 [oil-oil/wolfcha](https://github.com/oil-oil/wolfcha) 的 `.env.example` 里有 Supabase 配置，容易让人以为做这类游戏就得配数据库。把那个文件整体拆开看就清楚了：

| 配置 | 用途 | 属于哪一层 |
| --- | --- | --- |
| `STRIPE_SECRET_KEY` / `STRIPE_PRICE_ID` | 支付订阅 | 运营 |
| `WATCHA_CLIENT_ID` / `SECRET` | 第三方 OAuth 登录 | 运营 |
| `SUPABASE_URL` / `SERVICE_ROLE_KEY` | 数据库 + 认证 | 运营 |
| `MINIMAX_TTS_MODEL` | 语音合成 | 表现层 |
| `ZENMUX` / `DASHSCOPE` / `NEWAPI` 等 | LLM provider | AI 层 |

Supabase 在那里是和 Stripe、OAuth 并列的——它服务的是**公开运营的商业产品**（wolf-cha.com 是线上服务）所需的账号与订阅配额。狼人杀的规则本身一行都不需要它。

所以我们前六个阶段没有数据库，不是漏了，是范围不同。等到阶段 7 要做账号和计费时，才会因为**同样的运营原因**引入它。

## 5. 什么情况下需要重新审视本文档

以下任何一条成真，本文件的结论就要重新评估：

- 要做**线上多人对局**（真人对真人）——需要实时同步与权威服务端，引擎的运行位置会变
- 要做**排行榜或跨设备战绩**——对局数据就有了跨会话查询的需求
- 要做**对局数据分析**（比如统计各模型胜率并长期留存）

目前这三条都不在计划内。阶段 6 的「多模型对战胜率统计」是单机跑完即看的，不落库。
